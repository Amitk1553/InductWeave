# Decisions and assumptions

Where the brief was silent or something had to give, this is what was chosen and why.

## Structure
- The monorepo root is the workspace root (`backend/`, `frontend/`, `docs/`), not a nested `onboarding-orchestrator/` folder.
- Extra files beyond the listed layout: `routes/me.routes.js` (`/api/me`, dev role endpoint), `controllers/*`, `lib/{errors,access,dates}.js`, `services/taskLifecycle.service.js` (task edit/status rules, keeping `orchestrator.service.js` for plans), `db/queries/escalations.js`, `backend/openapi.yaml`, and a few small shared frontend components (`StatusBadge`, `StatCard`, `EmptyState`, `AiBadge`).
- Backend uses Express 5, Zod 4 and node-cron 4. Because `req.query` is read-only in Express 5, the validation middleware stores parsed input on `req.valid`.

## Data model
- Added columns not in the spec: `employees.manager_email` (managers are linked to reports by email when they first appear), `tasks.template_id` (compliance and de-duplication), `tasks.review_confirmed` (explicit HR confirmation without losing the `requires_review` flag).
- Dates are stored as `date` and handled as `YYYY-MM-DD` strings (a global `pg` type parser avoids timezone shifts).
- Confirming a task does not clear `requires_review`; approval only checks `requires_review AND confidence < 0.3 AND NOT review_confirmed`.
- Regenerating creates a new version. Older drafts are closed as `rejected` ("Superseded") so only one draft is actionable; approved plans cannot be regenerated (409).
- `npm run db:migrate` runs `src/db/migrate.js` (Drizzle's migrator on the app's own driver, same migrations folder) instead of `drizzle-kit migrate`, which always uses `pg` over port 5432.
- Migration `0000_init.sql` was generated by drizzle-kit and then hand-edited to prepend `CREATE EXTENSION IF NOT EXISTS vector` and append the audit immutability function and trigger. The vector size (768) is baked into that migration.

## Rules engine
- `applies_to.locations` uses normalised country names (`India`, `US`, `Canada`, `UK`); cities are mapped to them. `applies_to.roles` uses role tags derived by keyword (`engineering`, `manager`, `intern`, `sales`, ...), and a role can have several (an "Engineering Manager" gets both manager and engineering tasks).
- Added optional template fields: `excludes_roles` (interns skip first-week schedule, AWS, dev environment, PF/UAN) and `replaces` (the intern loaner laptop replaces the standard laptop and takes over its dependents).
- Unknown role or location: only role-/location-agnostic templates plus any known-location legal tasks, every task flagged (`Unknown role` / `Unknown location`) at confidence 0.45.
- Dependencies to templates not present in the plan are dropped (for example GitHub access depends on whichever background check applies).
- Start dates in the past are accepted. Due dates that have already passed when the plan is generated are moved to today and flagged, so HR can see the plan was adjusted.

## AI
- Defaults: `gemini-2.5-flash` and `gemini-embedding-001` at 768 dimensions. The embedding docs list `gemini-embedding-2` as the newest model; it is supported through task prefixes in the input text but was not exercised. `gemini-embedding-001` truncated vectors are normalised manually, as the docs require.
- The JSON schema given to Gemini uses plain strings (empty string instead of null) to stay within the supported schema subset; Zod converts empty strings to `null`.
- Only role, department, location and start date go to the model for checklist generation. Start date is included because the prompt template requires it; it is not an identifier.
- AI confidence is averaged with the rule confidence when an AI task matches a rule task, so the model's opinion influences the score but cannot replace the deterministic baseline.
- Chat injection handling chooses "refuse politely and audit" over "neutralise and answer", because a refusal cannot be talked around.
- An answer with no verifiable citation is treated as ungrounded and replaced by the standard refusal.
- A demo/eval hook, `?simulate=failure|malformed`, exists on plan generation. It is accepted only when `NODE_ENV=development`.
- The correction retry sends the validation error and the previous output (truncated) back to the model once.

## Auth and roles
- Roles are read from Clerk on each request through a 30 second in-memory cache (invalidated on role switch).
- There is no `it` role in Clerk, so IT-assigned tasks are completed by HR users.
- The dev role switcher is a frontend control shown only in Vite dev builds, and the backend route is registered only when `NODE_ENV=development`.
- Managers chatting or HR chatting must pass `employeeId` (or have a linked employee record); employees always chat as themselves.

## API and operations
- General rate limit is 300 requests per 15 minutes per IP (the brief suggested 100; a dashboard page issues several requests). Chat is limited to 40 and plan generation to 20 per 15 minutes.
- Chat "Contact HR" creates one open escalation per employee at a time (de-duplicated by type), so a second question while the first is open reuses it.
- Audit writes are best-effort: a failure is logged at error level but does not fail the user's request.
- The seed script refuses to run when `NODE_ENV=production` unless `--force` is passed. It is deterministic and does not call Gemini.
- The escalation scan marks overdue only `active`/`in_progress` tasks; `pending` tasks (blocked) are not overdue, their blocker is.

## Evaluation
- `npm run eval` creates temporary employees under `@eval.invalid`, deletes them afterwards (cascading to plans, chat and escalations) and reports only what it measured. Audit rows it creates remain, because the audit table is immutable by design.
- Checklist scenarios report the mode (`ai` or `fallback`) so a run where Gemini was unavailable cannot be mistaken for an AI result.
